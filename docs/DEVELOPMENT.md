# 개발 및 배포 가이드

사용자 설치·실행·사용법은 [README](../README.md), 에이전트 작업 규칙은 [AGENTS](../AGENTS.md)를 참고한다. 개발 작업은 [프로젝트 문서 집합](worktree/project.json), 후속 후보는 [ROADMAP](../planning/ROADMAP.md)에서 관리한다.

0.24.0부터 프로젝트 문서 집합을 사용한다. 아래 버전별 과거 기록의 WBS·탐색기·표 셀 저장 설명은 당시 구현 기록이며 현행 규격은 [PROJECT_FORMAT](PROJECT_FORMAT.md)과 ADR 0015다.

## 개발 환경과 실행

Windows x64에서 Node.js 24, Rust stable, Visual Studio C++ 빌드 도구와 WebView2를 사용한다. 앱은 Tauri 2·Vite·React·TypeScript로 구성되어 있다. 프런트엔드 전체를 TypeScript로 작성하고 strict 타입 검사에 포함한다. Node 실행용 개발 스크립트와 기존 단위 테스트는 .mjs를 유지한다.

```powershell
npm ci
npm run tauri dev
```

## 브랜치 운영

작업 시작·재개 시 AGENTS.md와 관련 지침을 확인한다. 문서·작업 규칙만 변경하면 검증 후 바로 커밋할 수 있다. 기능 개발·수정·리팩터링 등 소스코드 작업은 박대호의 명시적인 커밋 지시를 기다린다. 문서와 코드가 섞인 변경은 코드의 커밋 지시를 따른다. 커밋 허가는 푸시·병합·배포의 자동 허가가 아니며 아래 예시는 해당 행위가 허용된 범위에서만 실행한다.

- main: 검증을 마친 정식 배포 기준. 직접 기능을 개발하지 않는다.
- develop: 완료한 기능을 모아 다음 목표를 확인하고 유지보수하는 상시 브랜치. main에 병합한 뒤에도 남겨 둔다.
- 기능·수정·문서 작업은 develop에서 직접 진행하고 목적별 커밋으로 구분한다. 기능별 브랜치는 만들지 않는다. 기존 브랜치·병합 기록은 보존한다.

기능마다 구현·관련 검증·문서 갱신 결과를 정리하고 명시적 커밋 지시를 받은 뒤 별도 커밋으로 남긴다. 해당 기능의 커밋 후 다음 기능을 진행한다. 순차 개발 요청만으로 커밋을 허가받았다고 판단하지 않으며, 기능별 커밋까지 명시적으로 일괄 승인한 범위는 재승인을 요구하지 않는다. 사용자가 원하는 목표에 도달하고 통합 확인을 마쳤을 때 develop을 main에 병합한다. 단순 문서 변경은 develop에 직접 커밋할 수 있다. 병합 완료 후에도 develop에서 다음 작업을 계속하며 별도 release 브랜치는 기본적으로 사용하지 않는다.

```powershell
git switch develop
git status --short --branch
# 기능 하나를 구현·검증하고 관련 문서를 갱신한다.
# 명시적 커밋 지시 후 해당 기능 파일만 선택해 커밋한다.
# 다음 기능도 같은 절차로 진행한다. 푸시는 별도 지시 범위를 따른다.
```

## 버전 변경과 자동 배포

버전 결정 기준과 변경 이력 운영 규칙은 [AGENTS의 버전과 릴리즈 운영](../AGENTS.md#버전과-릴리즈-운영)을 따른다. package.json을 기준으로 동기화 명령을 사용하며 앱 버전과 WBS schema_version은 별개다.

1. develop에서 목표 기능을 통합하고 사용자 확인을 받는다.
2. CHANGELOG.md의 Unreleased 내용을 새 버전과 날짜 아래로 옮긴다.
3. 필요한 버전 변경은 `npm run version:set -- X.Y.Z`로 동기화한다. 로컬 검사·테스트·프런트엔드 빌드 및 필요한 실제 동작 검증을 수행하고 커밋 승인을 받아 develop에 커밋한다.
4. 배포가 승인되면 develop을 main에 병합하고 main을 푸시한다. 수동으로 릴리즈 태그를 만들 필요는 없다.

```powershell
git switch develop
npm run version:check
npm test
npm run build
# 변경 이력·문서를 갱신하고 검증 후 커밋·사용자 확인을 마친다.
git push origin develop
git switch main
git merge --no-ff develop
git push origin main
git switch develop
```

.github/workflows/release.yml은 main 갱신 시 실행된다. GitHub의 일반 병합·스쿼시 병합 모두 main push 이벤트로 처리된다. main 직접 푸시도 같은 이벤트이므로 운영 규칙상 main 직접 개발을 금지한다.

이미 공개 Release가 있는 버전이면 빌드와 게시를 건너뛴다. 새 버전이면 테스트·버전 검사·Windows x64 NSIS 빌드가 모두 성공한 뒤, 해당 main 커밋에 vX.Y.Z 태그와 GitHub Release를 생성한다. 같은 버전의 미게시 태그가 이미 있으면 잘못된 커밋 배포를 막기 위해 실패 처리한다. API·태그 조회 실패도 배포 생략으로 숨기지 않고 실패로 표시한다.

develop·기능 브랜치 갱신이나 수동 태그 푸시는 정식 배포를 실행하지 않는다. 버전 변경 명령 자체는 커밋·병합·게시를 수행하지 않는다. 진행 상태는 저장소 Actions에서 확인한다. 게시한 태그·설치 파일은 덮어쓰지 않고 새 버전으로 수정 배포한다. 앱 내부 업데이트는 아래 서명 배포 절차를 사용한다.


## 서명 업데이트

Tauri 공식 updater를 Rust 명령에서 사용한다. GitHub 최신 정식 릴리즈를 SemVer로 비교하고 newer 버전의 latest.json이 있을 때만 설치를 준비한다. 개발 버전이 앞서면 다운그레이드하지 않는다. 구형 릴리즈에 manifest가 없으면 수동 설치로 안내하며 네트워크 실패는 최신 상태로 취급하지 않는다.

- 공개 키: src-tauri/tauri.conf.json의 plugins.updater.pubkey.
- 로컬 암호화 개인 키와 암호: Git에서 제외한 .local/updater/worktree.key, .local/updater/password. 별도 안전한 장소에 백업하고 임의 재생성하지 않는다.
- Actions secrets: TAURI_SIGNING_PRIVATE_KEY(키 파일 내용), TAURI_SIGNING_PRIVATE_KEY_PASSWORD(암호). 빌드 프로세스 환경에만 전달한다.
- 실제 설치 검증을 위한 선택적 로컬 빌드는 같은 환경 변수를 설정해 npm run tauri build -- --ci --bundles nsis를 실행한다. 키나 암호를 명령문·로그에 직접 작성하지 않는다.
- scripts/update-manifest.mjs가 설치 파일의 .sig와 현재 버전을 연결해 latest.json을 만든다. main 워크플로는 설치 exe·.sig·latest.json을 같은 Release에 게시한다.
- 앱은 HTTPS 고정 저장소에서 확인하고 버전·설치 URL 일치를 검사한다. 다운로드 후 Tauri 공개 키 검증을 통과해야 설치한다. 설치 전 사용자 확인을 받고 진행률을 표시한다.
- 문제 제보는 고정 저장소의 새 issue 작성 URL만 연다. 문서 내용·경로는 수집하지 않는다.
- 공개 릴리즈를 만들지 않는 로컬 검증으로 실제 배포 후 업그레이드 성공까지 주장하지 않는다. main 게시 후 구버전 설치 앱에서 조회→다운로드→서명→설치→재실행 인수를 수행한다.

버전 증가와 릴리즈 게시를 분리한다. 개발 중 기능 추가에도 MINOR를 올리고 변경 내용은 Unreleased에 개발 버전과 함께 기록한다.

## 0.5.1 설정 저장과 프로필 이전

앱 식별자 io.github.devpumpkin0113.worktree와 게시자 DevPumpkin0113을 사용한다. 설정 경로는 식별자와 독립적인 %LOCALAPPDATA%/Worktree/settings.json이다. schemaVersion 2, language(ko/en), idSeparator(none/hyphen), detailMode(sidebar/modal), autoCheckUpdates(boolean)를 저장한다. 기존 v1은 한국어 기본값으로 읽고 다음 저장에서 v2로 기록한다.

창 자동 생성을 끄고 Rust setup에서 데이터 디렉터리를 선택한다. JSON이 없고 이전 local.toothless.worktree/EBWebView가 있으면 그 프로필로 한 번 실행하고 기존 origin의 localStorage를 읽어 initialize_settings로 저장한다. JSON이 있으면 이전 localStorage보다 우선하며 이후 Worktree/EBWebView를 사용한다. 이전 프로필을 복사하거나 삭제하지 않는다. 설치 EXE 이름과 NSIS의 Worktree 제거 프로그램 키는 동일해 기존 설치 위치를 유지한다. 식별자가 달라 구버전과 신버전의 단일 인스턴스 키는 다르므로 업데이트 전 기존 앱은 종료한다.

설정 파일은 크기가 작은 serde JSON이며 tempfile을 이용해 같은 디렉터리에서 동기화 후 교체한다. UI는 저장 성공 후 상태를 반영하고 저장을 직렬화한다. 손상·잘못된 값은 settings.invalid-*.json으로 보관한 뒤 기본값으로 복구하고 안내한다. 지원하지 않는 schemaVersion이나 읽기 오류는 원본을 유지하며 설정 변경을 막는다. 수동 편집은 앱 종료 후 수행한다.

## 0.5.1 인수 확인과 0.5.2 유지보수

### 공수 기반 지표 조사 (2026-10-20, 참고 자료)

- [Microsoft Project의 Percent Work Complete](https://support.microsoft.com/en-gb/project/percent-work-complete-fields): 실제 공수/공수로 작업량의 완료 비율을 추적한다. 기간 기준 percent complete와 구별한다.
- [Smartsheet 부모 집계](https://help.smartsheet.com/articles/765753-parent-rollup-functionality): 하위 작업 기간과 개별 완료율을 가중해 부모 완료율을 계산한다. 인시 기준과는 다른 지표다.
- [Atlassian 번다운 안내](https://www.atlassian.com/agile/tutorials/burndown-charts): 시간·스토리 포인트 등의 추정 단위로 남은 작업량을 추적한다. 상단 백분율 카드와 동일한 표현은 아니다.

Worktree의 공수 지표는 완료된 task의 예상 공수/전체 task의 예상 공수이며 진행 중의 실제 투입 공수·부분 완료율을 수집하지 않는다. 규모 차이를 가중하는 용도는 있지만 위 도구의 실제 공수 지표와 같다고 설명하지 않는다. 현재 WBS는 일반 작업 52개의 공수가 모두 미정이므로 이 지표는 산정 불가다. 기본 화면 유지·선택적 표시·제거 여부는 사용자 결정 전까지 변경하지 않는다. 사용자 지정 작업 유형은 별도 미선택 후보로 유지한다.

## 0.16.0 앱 설정·프로젝트 관리 진입점

상단은 앱 설정, 좌측 열린 문서 이름 오른쪽의 아이콘은 프로젝트 관리로 구분한다. 버튼 문구는 툴팁과 접근성 이름으로 제공한다. 프로젝트 관리 UI는 components/project에서 관리하고 현재 WBS 메타데이터와 공통 작업 유형·상태를 조회한다. 유효한 문서가 없으면 진입 버튼을 비활성화한다. 프로젝트 폴더 열기·독립 설정 파일·편집·저장은 아직 구현하지 않는다. 프로젝트 관리는 모달 대신 메인 콘텐츠 페이지로 표시한다. 좌측 메뉴로 다른 페이지에 이동하며 앱 설정을 닫으면 원래 프로젝트 관리 페이지가 유지된다. 새 색상 상수 없이 공용 테마 변수를 사용한다.

좌측 프로젝트 트리는 프로젝트 제목을 루트로 접기·펼치기를 지원하는 UI 시안이다. 현재 활성 WBS 파일 한 개를 들여쓰기하여 표시하고 클릭하면 작업 보드로 이동한다. 프로젝트 루트 탐색·내부 파일 수집·별도 프로젝트 상태는 아직 구현하지 않았고 하단 문서 탭·세션 계약은 유지한다. ProjectFiles와 ProjectEntry를 역할별로 분리한다.

작업 보드·작업 목록 제목 오른쪽은 CompactProgress에서 전체 일반 작업 기준 완료/전체·진행률을 표시한다. 필터·그룹·마일스톤은 집계 기준에 영향을 주지 않는다. 기존 Metrics 요약 카드는 인사이트 본문으로 이동하고 공수 사용 여부를 유지한다. 인사이트 상단 요약은 실제 데이터이며 하단 분석 차트는 미연결 시안이다. 워크스페이스 장식 배지는 제거했다.

## 0.16.1 한국어 리소스 분리

프런트엔드 한국어 표시 문구는 src/i18n/ko.ts에 두고 src/i18n/messages.ts를 통해 참조한다. 툴팁·접근성 이름·SVG 안내·검증 및 저장 오류를 포함한다. Rust 네이티브 대화상자·오류·제보 양식은 src-tauri/src/i18n/ko.rs에 분리한다. UI 마크업은 기존 컴포넌트와 SVG 렌더러에 유지하고 문자열 삽입 시 기존 이스케이프를 적용한다.

WBS 규격 상수는 src/domain/wbs-schema.ts에서 공유하며 번역 리소스와 분리한다. 언어 전환·언어 설정·날짜 및 숫자 로케일 변경은 아직 지원하지 않는다. 한국어 오류 정규식은 기존 계약을 보존하며, 실제 언어 전환 전에 오류 코드를 도입해야 한다. 결정 근거는 docs/adr/0006-korean-message-resources.md를 따른다.

한국어 분리 검증: 프런트엔드 테스트 67개·Rust 19개·strict 타입 검사·TS/CSS 포맷 검사·버전 동기화·Vite 빌드 통과. Rust의 실네트워크·서명 설치 파일 검증 2개는 기존 ignored 상태로 실행하지 않았다. 실제 WebView2 UI 확인과 Windows 설치 빌드는 수행하지 않았다.

영어 리소스는 src/i18n/en.ts와 src-tauri/src/i18n/en.rs에 같은 키·함수로 준비했다. TS는 satisfies typeof ko로 검사하고 테스트에서 키·함수 인자·서식 값 보존을 확인한다. Rust en 모듈은 테스트에서만 컴파일하며 런타임은 ko를 유지한다. 규격 제목 ## 작업 목록과 사람 이름은 영어 안내에서도 보존한다. 아직 언어 전환을 지원하지 않으므로 영어 화면을 켜는 코드 변경은 하지 않는다.

영어 리소스 추가 후 프런트엔드 69개·Rust 20개 테스트, 타입·포맷·버전 검사 및 Vite 빌드 통과. 외부 네트워크·서명 설치 파일 검증 2개는 기존 ignored 상태다. 언어 선택과 실제 영어 UI 검증은 아직 수행하지 않았다.

## 0.18.0 폴더 프로젝트

하단 ProjectDock은 파일 대신 폴더를 탭으로 표시한다. +는 pick_project, 열기·복원은 scan_project 명령을 사용한다. src-tauri/src/projects.rs는 하위 WBS를 검색하고 경로를 정규화한다. 링크·junction·숨김 이름 폴더 및 node_modules·target·dist는 제외하며 파일 2,000개·폴더 10,000개·깊이 64로 제한한다. 실패 시 기존 프로젝트를 유지하고 문제 패널로 안내한다.

좌측 ProjectFiles는 상대 경로 목록이며 선택한 WBS의 보드·목록·인사이트를 표시한다. 빈 프로젝트도 유지하고 새로고침으로 파일 목록을 갱신한다. 활성 문서 내용은 기존 자동 갱신을 유지한다. 원본과 프로젝트 폴더에는 쓰지 않는다. 직접 연 Markdown은 기존 호환 항목으로 유지한다.
