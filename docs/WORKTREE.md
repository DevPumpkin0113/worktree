# 공통 Worktree 작업 구성 기준

여러 프로젝트에서 재사용하는 작업 관리 지침이다. 프로젝트에 적용할 때는 프로젝트별 설정과 개발 영역을 별도 문서에 정리하고 이 기준과 함께 사용한다. 아래 설정 항목은 확인할 목록이며 특정 값을 자동으로 적용하는 기본값이 아니다.

## 1. 프로젝트별 설정

프로젝트명, 루트 위치, 관리 데이터 위치, 작업 ID 프리픽스·표시 구분자, 날짜·시간 형식·기준 시간대, 담당자, 작업 유형·우선순위·라벨은 해당 프로젝트에서 합의한 값을 사용한다. 기존 프로젝트는 CLI 조회 결과와 현재 문서를 먼저 확인한다. 신규 프로젝트는 사용자가 지정하지 않은 필수 설정을 확인한 뒤 초기화한다.

다음 운영 방식은 이 공용 문서의 기준으로 사용하되 프로젝트에서 별도 합의한 규칙이 있으면 그 규칙을 따른다.

- 예상 작업시간은 사용하지 않는다.
- 작업 등록 시 날짜는 비워두고 실제 착수 시 시작일·예정 종료일을 지정한다.
- 마일스톤 일정은 별도 합의 전까지 지정하지 않는다.
- 실제 ID와 데이터 위치는 생성·조회 결과를 사용하고 다른 프로젝트의 값을 복사해 적용하지 않는다.

여기서 Worktree는 작업 관리 도구를 의미한다. Git의 별도 체크아웃 기능인 Git worktree와 구분한다.

## 2. 마일스톤을 나누는 기준

마일스톤은 **완료했을 때 무엇을 사용할 수 있게 되는지**를 기준으로 지정한다. 사용자 기능 이전의 개발 기반 단계라면, 어떤 개발·실행·검증이 가능해지는지를 결과로 정의한다.

- 구현 영역별로만 마일스톤을 나누기보다, 필요한 구성 요소를 연결한 사용 가능한 결과를 묶는다.
- 마일스톤 하나에는 명확한 목표와 범위를 두고, 완료 여부를 확인할 수 있는 기준을 정한다.
- 너무 커서 결과를 확인하기 어렵다면 독립적으로 검증 가능한 단계로 나눈다.
- 기술 조사만 필요한 경우에는 원칙적으로 해당 결과를 지원하는 작업으로 배치한다.
- 순서는 기능 간 의존성과 기술 위험을 고려한다. 후속 구현의 방향을 바꿀 수 있는 검증은 앞 단계에 둔다.
- 제목은 짧고 일관된 명사형으로 작성한다. 세부 기술·작업 목록은 제목에 나열하지 않는다.

한쪽 구현만 끝난 경우와 실제 연결까지 검증된 경우를 구분한다. 관련 작업이 완료되었더라도 마일스톤의 최종 사용 흐름을 충족하는지 확인한다.

## 3. 작업으로 등록하는 내용

작업은 **기능·문서·환경 구성처럼 명확한 결과물이 있는 변경 단위**로 등록한다.

등록 대상은 기능 구현·수정, 오류 수정, 기존 기능 개선, 문서 작성·수정, 개발환경·빌드 설정이다. 단순한 대화·아이디어·일상적인 진행 보고는 그 자체로 작업으로 만들지 않는다.

다음 기준으로 크기를 조정한다.

- 목적과 산출물이 하나의 흐름으로 설명되면 한 작업으로 묶는다.
- 담당 영역·의존관계·검증 방법이 달라 독립적으로 추적할 필요가 있으면 나눈다.
- 여러 기능 전체를 한 작업으로 묶거나, 파일·함수별로 기계적으로 잘게 나누지 않는다.
- 필요한 검증·테스트·오류 확인은 각 작업의 수행 범위와 완료 조건에 포함한다. 기본적으로 별도 검증·테스트 작업을 만들지 않는다.
- 기술 조사는 해당 구현에 포함한다. 구현 방향을 정하기 위한 독립 실험이 꼭 필요하다면 별도 작업으로 등록할지 먼저 논의한다.
- 필요한 문서 갱신은 구현 작업에 포함할 수 있다. 독립적인 가이드·설계 문서처럼 별도 결과물이 있으면 문서 작업으로 등록한다.
- 당장 구체화할 수 없는 먼 후속 범위는 마일스톤 수준으로 유지하고, 착수할 범위부터 작업으로 상세화한다.

## 4. 개발 영역을 구분하는 기준

마일스톤 안에서 서버·클라이언트·공통 규격 등 실제 프로젝트의 개발 영역을 필요에 따라 분리한다. 구현 영역은 프로젝트별 라벨로 구분하고 동일한 마일스톤에 연결한다. 실제 연결 상태의 통합 확인은 관련 작업의 완료 조건에 포함한다.

각 영역의 책임과 경계를 먼저 정의한다. 구성 요소 사이의 계약이 필요하면 요청·응답·이벤트·오류 형식 등을 합의하고, 각 영역이 그 계약에 따라 구현되도록 한다. 구체적인 앱·모듈 이름과 라벨은 프로젝트 문서에 둔다.

모든 기능을 반드시 같은 수의 작업으로 나눌 필요는 없다. 작은 변경은 한 작업으로 묶고 관련 라벨을 함께 지정한다. 의존관계는 실제 선행 결과가 필요한 작업 사이에만 설정한다.

## 5. 작업을 작성하는 기준

각 작업에는 다음 내용이 드러나야 한다.

| 항목 | 작성 기준 |
| --- | --- |
| 제목 | 수행 결과를 구체적으로 표현 |
| 목적 | 해결할 문제 또는 필요한 이유 |
| 범위 | 변경할 내용과 필요한 경계 |
| 완료 조건 | 관찰·검증할 수 있는 결과 |
| 검증 방법 | 결과를 확인할 검사 또는 재현 절차 |
| 분류 | 소속 마일스톤, 유형, 담당자, 우선순위, 관련 라벨 |
| 참고·의존관계 | 필요한 문서·계약·선행 작업 |

유형은 작업의 성격, 라벨은 구현·기능 영역을 표현한다. 담당자는 실제 책임 주체를 지정하며, 사용자가 수행하기로 하지 않은 일을 임의로 사용자 담당으로 배정하지 않는다.

## 6. 등록과 변경 원칙

마일스톤·작업 구성안을 제시하는 것과 실제 등록은 구분한다. 목록 검토 요청만으로 등록하지 않고, 추가 요청이 있을 때 합의한 범위를 반영한다.

등록 전 기존 항목과 중복 여부를 확인한다. 요구사항이 바뀌면 관련 작업의 범위와 완료 조건도 갱신한다. 차단된 경우 원인과 해제 조건을 기록한다.

대화의 지시 횟수를 작업 수로 삼지 않는다. 같은 목적과 사용 흐름을 다듬는 문구·배치·여백·상태 표시와 공통 요소 조정은 기존 작업에 묶는다. 목적·산출물·완료 조건을 독립적으로 관리할 필요가 있을 때만 새 작업으로 분리한다.

작업을 실제로 시작해 `doing`으로 변경할 때 시작일과 예정 종료일을 함께 지정한다. 시작일은 실제 착수일이며, 날짜는 프로젝트에서 합의한 시간대를 기준으로 한다. 아직 착수하지 않은 작업은 날짜를 비워둔다. 예상 작업시간은 계속 사용하지 않는다.

실제 완료일이 지정한 종료일보다 늦어지면 완료 처리 시 종료일을 실제 완료일로 갱신한다. 예정일보다 일찍 완료하거나 같은 날 완료하면 기존 종료일을 유지한다. 기존 예정일과 변경 이유는 별도로 기록하지 않는다. 실제 완료는 아래 사용자 확인·승인을 포함한 완료 기준을 따른다.

완료 흐름은 **구현 → 자체 확인 → 사용자 확인·승인 → 완료**로 진행한다. 작업 수행자는 필요한 검사와 동작 확인을 수행하고 결과·남은 제약·사용자 확인 방법을 전달한다. 자체 확인만으로 사용자 승인을 대신하지 않는다.

현재 별도 승인 대기 상태는 없으므로 사용자 확인 전에는 `doing`을 유지하고 댓글에 자체 확인 결과와 승인 대기임을 기록한다. 사용자가 확인·승인한 뒤 `done`으로 변경한다. 수정 요청이 있으면 해당 범위와 완료 조건에 맞춰 보완한다.

구현을 계속 진행할 수 있는 권한과 작업을 `done`으로 처리하는 승인은 구분한다. 여러 작업의 일괄 구현을 허용받았다는 이유만으로 사용자 확인까지 끝났다고 간주하지 않는다.

- 기본적으로 승인 대기 중인 선행 작업에 의존하는 후속 작업은 대기한다. 해당 선행 작업과 무관한 승인 범위의 작업은 진행할 수 있다.
- 사용자가 승인 전에도 의존 작업의 연속 구현을 허용한 경우, 선행 작업의 자체 확인과 메인 검토를 통과한 뒤 후속 구현을 진행할 수 있다. 선행 작업은 승인 대기를 유지하며, 후속 작업 댓글에 아직 승인되지 않은 선행 결과를 사용한다는 점을 기록한다.
- Worktree의 의존성 검증이 후속 착수를 허용하지 않으면 의존관계를 삭제하거나 선행 작업을 거짓 완료 처리하지 않는다. 사용자에게 제약을 알리고 승인 또는 작업 구성 조정 후 진행한다.
- 선행 결과가 수정되면 영향을 받은 후속 작업을 다시 확인한다. 연결된 최종 결과는 통합 검증하고, 사용자 승인 후 승인된 작업만 완료 처리한다.

구체적인 마일스톤·작업 목록과 진행 기록은 Worktree에 유지한다. 이 문서는 목록을 복제하지 않고 구성 기준만 설명한다. Worktree 데이터 변경은 CLI를 사용한다.

## 7. 에이전트 위임 시 작업과 기록

메인 단독 수행과 서브에이전트 위임의 선택, 역할 및 검토 절차는 `AGENTS.md`를 따른다. Worktree는 공통 작업판과 기록으로 사용하며, 에이전트를 실행시키는 메시지 전달 장치로 사용하지 않는다.

- 메인은 기존 작업의 범위·완료 조건·선행 작업을 확인하고 실제 작업 ID를 서브에 전달한다. 에이전트를 호출했다는 이유만으로 새 작업이나 별도 테스트·리뷰 작업을 만들지 않는다.
- 담당자는 프로젝트에서 합의한 책임 주체를 유지한다. 임시 서브에이전트를 호출할 때마다 담당자를 바꾸거나 새 담당자를 만들지 않는다.
- 작업 상태·명세·댓글의 CLI 변경은 기본적으로 메인이 담당한다. 서브는 구현·검증 결과를 메인에 보고한다. 서브가 Worktree를 직접 갱신해야 하면 대상 작업과 변경 필드를 명시적으로 배정해 동시 쓰기를 피한다.
- 여러 서브가 같은 작업에 기여하면 메인이 결과를 통합한다. 실제 저장 충돌이 발생하면 최신 데이터를 다시 읽고 변경 의도를 확인한 뒤 처리한다.
- 댓글에는 중요한 범위·설계 결정, 차단 원인, 검증 결과, 보완 내용과 사용자 승인 대기를 기록한다. 에이전트 간 대화 전문이나 매 호출의 진행 보고를 그대로 복제하지 않는다. 댓글 작성자는 프로젝트에서 합의한 이름을 사용한다.
- 검증 결과에는 완료 조건별 결과, 실제 실행한 검사와 결과, 미실행 검사·제약 및 사용자 확인 방법을 남긴다. 상세 로그는 필요하면 파일을 참조한다.
- 서브의 구현 완료와 메인의 검토 통과는 자체 확인 단계다. 승인 대기, 후속 작업 착수와 완료 처리는 6절의 기준을 따른다.
- 서브에이전트 종료·교체 후에는 Worktree의 현재 명세와 기록을 다시 확인한다. 중단된 실행의 보고만으로 완료를 추정하지 않는다.

## 8. 변경 요청과 오류 처리 기준

| 상황 | 처리 방식 |
| --- | --- |
| 승인 전, 원래 완료 조건을 충족하지 못함 | 기존 작업에서 보완 |
| 승인 전, 별도 기능·개선 요청 발생 | 새 작업 추가 |
| 완료 후 버그 발견 | `bug` 작업 생성 |
| 완료 후 사용성·성능 개선 | `improvement` 작업 생성 |

구분 기준은 기존 작업의 완료 조건에 포함되는 내용인지다. 작은 조정은 기존 작업에 반영하고, 독립적인 기능·개선은 새 작업으로 분리한다. 승인 전후만으로 모든 변경을 새 작업으로 나누지는 않는다.

관련 마일스톤이 진행 중이면 새 작업을 해당 마일스톤에 추가한다. 이미 완료한 마일스톤은 유지하고, 완료 후 발견한 버그·개선은 다음 개선·패치 마일스톤에 등록한다. 원래 작업을 참조해 변경 배경을 추적할 수 있게 한다.

독립적인 작업으로 분리하는 것은 처리를 뒤로 미룬다는 뜻이 아니다. 작업 순서는 영향과 우선순위에 따라 정하며, 긴급한 버그는 우선 처리한다.

새 작업에도 필요한 검증·테스트를 포함하고 사용자 확인·승인 후 완료 처리한다. 실제 Worktree 등록은 합의한 요청 범위에 따라 진행한다.
